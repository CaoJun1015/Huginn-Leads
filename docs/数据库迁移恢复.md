# 数据库迁移失败与旧库恢复

适用范围：HL-REL-002，2026-09-18。源码环境已用临时 SQLite 和合成数据验证；生产库与 Windows 发布包现场恢复仍待验收。本说明不授权操作生产数据。

## 新运行器的行为

每个版本使用一个 `BEGIN IMMEDIATE` 写事务，包含结构变更、数据回填及 `schema_migrations` 登记。运行器使用 `sqlite3.complete_statement` 和逐条 `execute`，不使用会隐式提交的 `executescript`；迁移 SQL 不得自行 BEGIN/COMMIT/ROLLBACK/SAVEPOINT，违反时会失败并回滚。已经完整提交的版本保留，失败版本全部回滚，修复磁盘、权限或 SQL 等实际故障后可重新启动。

错误示例：`schema_migration_failed version=4 code=SQLITE_ERROR`。输出包含版本、错误类别和恢复说明路径，不包含 SQL、消息正文或原始异常文本。运行器不会吞掉重复列错误，也不会推测版本号并自动补登记。

## 识别历史半应用状态

旧运行器可能已经提交结构/回填，却没有提交版本登记。例如：登记只有 1、2、3（或 1、2、3、5），而 `leads` 已含 `sender_id`、`sender_name`，重试 v4 将遇到重复列；也可能仅添加了其中一列。数据库完整性为 ok 不代表业务回填或迁移登记完整。

1. 停止 Huginn Leads 和所有访问该库的程序，确认没有旧进程自动重启。保留原库及 WAL/SHM 文件；不要删除数据库或仅拷贝一个仍在使用中的 `.db` 文件。
2. **先备份再核对。** 使用 SQLite backup API 为现状生成独立副本（包括已提交的 WAL 内容）；目标必须是新文件。以下片段在源码项目目录执行，路径请替换为已经确认的目标，切勿覆盖既有备份：

   ```python
   from contextlib import closing
   from pathlib import Path
   import sqlite3

   source = Path("data/huginn-leads.db").resolve()
   target = Path("backups/before-migration-recovery.db").resolve()
   assert source.is_file() and not target.exists()
   target.parent.mkdir(parents=True, exist_ok=True)
   with closing(sqlite3.connect(source.as_uri() + "?mode=ro", uri=True)) as src:
       with closing(sqlite3.connect(target)) as dst:
           src.backup(dst)
           assert dst.execute("PRAGMA integrity_check").fetchone()[0] == "ok"
   ```

3. 在副本上只读核对以下结果（不打印业务正文）：

   ```sql
   PRAGMA integrity_check;
   PRAGMA foreign_key_check;
   SELECT version, applied_at FROM schema_migrations ORDER BY version;
   PRAGMA table_info(leads);
   PRAGMA table_info(sources);
   PRAGMA table_info(raw_messages);
   PRAGMA table_info(external_sources);
   PRAGMA table_info(external_records);
   SELECT type, name, tbl_name, sql FROM sqlite_master
     WHERE type IN ('table', 'index') ORDER BY type, name;
   SELECT count(*) FROM sources;
   SELECT count(*) FROM tasks;
   SELECT count(*) FROM raw_messages;
   SELECT count(*) FROM leads;
   ```

   将结构与本项目对应版本的迁移 SQL 比较。v4 两个字段均存在时，可在副本上统计回填不一致项，而不输出字段值：

   ```sql
   SELECT count(*) FROM leads l JOIN raw_messages r ON r.id=l.message_id
   WHERE l.sender_id IS NOT r.sender_id OR l.sender_name IS NOT r.sender_name;
   ```

   字段齐全、回填计数为 0 或完整性检查通过，**均不能单独作为补版本号的依据**。不要再次执行原脚本来“试试看”，不要跳过失败语句后直接登记成功。

## 已验证的保守恢复路径

使用**已知完整、升级之前的备份**，先在独立临时目录复制该备份并使用新运行器升级，核对完整性、外键、来源/任务/原文/线索数量，以及人工状态、备注、更正值、已读时间和关联关系。正常升级后重复迁移必须无变化。自动测试覆盖完整 v1—v4 升级，以及 v4 部分应用、全应用未登记、v5 已登记但 v4 缺失三种故障形态。

只有已确认备份完整、且备份之后没有新增业务记录，或者已由负责人处理好这段数据差异时，才使用该备份恢复。备份之后的消息和人工修改不会自动合并；不能把回退到旧备份描述为无损修复。

源码环境停机后的已有恢复入口：

```powershell
.\.venv\Scripts\python.exe scripts/restore.py <已核对的完整备份.db>
```

该命令会保存 `backups/before-restore-*.db`，但其现有校验仅检查 SQLite 完整性，**不能代替上述结构、版本和业务核对，也不负责可靠检测应用是否停机**。首次启动使用新迁移运行器；核对版本为 1—5、完整性 ok、外键检查无结果、业务数量及人工字段符合已确认的恢复点，再进行第二次启动核对。不要以运行旧版程序代替恢复流程。发布包无 Python 恢复及严格停机检测属于 HL-REL-008，尚未完成。

没有完整旧备份、发现备份之后有未保全的数据、外键或回填异常、结构无法解释时，保持停机并保留现状副本，交由维护人员在副本上逐项核对和制定数据保全方案；本轮不提供未经验证的自动补列、删列或补版本号功能。

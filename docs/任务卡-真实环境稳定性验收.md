# 任务卡：真实 QQ 多账号与 72 小时稳定性验收

| 项目 | 内容 |
|---|---|
| 编号 | HL-OPS-001 |
| 优先级 | P0 |
| 状态 | 待执行 |
| 基线版本 | `9ecf121` |
| 执行环境 | Windows 本机、Huginn Leads、NapCatQQ、两个获准测试 QQ |
| 预计周期 | 准备与场景测试半天，连续运行 72 小时 |

## 目标

证明 Huginn Leads 在真实 QQ 接入下能持续做到：来源范围不串、消息不重复、断线有记录、失败可发现、备份可恢复。完成本卡前不增加 OCR、LLM、主动通知或新消息平台。

## 前置条件

- 已确认测试用途、NapCatQQ 实际版本及适用授权。
- 准备两个测试 QQ、两个获准测试群，以及可辨认但不含真实业务信息的唯一测试字符串。
- 两个账号使用同一个 OneBot WebSocket 地址，并使用与 `.env` 一致的 Token。
- 正式测试前创建一次工作台备份；测试截图和记录不得包含 Token、真实聊天正文或不必要的身份信息。

## 执行步骤

### 1. 固定基线

- [ ] 确认 `git status --short` 无输出，HEAD 为本卡记录的基线或其后续修复提交。
- [ ] 运行后端测试、规则样本、性能脚本和前端生产构建。
- [ ] 记录 Python、NoneBot2、OneBot 适配器、NapCatQQ 与 Node.js 实际版本。
- [ ] 在“运行与数据”创建备份，记录文件名、大小和创建时间。

### 2. 验证账号与来源边界

- [ ] 同时连接两个 QQ，确认工作台显示两个独立账号。
- [ ] 刷新来源，确认新群和联系人默认关闭。
- [ ] 每个账号只开启一个获准测试群，并分别创建任务。
- [ ] 在启用群、未启用群、未启用好友私聊中发送不同的唯一测试字符串。
- [ ] 确认只有启用来源的消息进入原文和线索；数据库、控制台及持久日志中不存在未启用来源的测试正文。
- [ ] 修改群名或本地备注后刷新，确认历史关联仍使用稳定 ID，没有串到另一账号。

### 3. 验证处理闭环

- [ ] 向启用群发送匹配、冲突、信息不完整、多行多价格各一条测试消息。
- [ ] 重复上报同一原生消息，确认原文、作业和线索不重复。
- [ ] 暂停来源后继续发送，确认新消息不入库；重新启用后只接收后续新消息。
- [ ] 暂停任务时发送消息，确认不产生新线索；重新启用不隐式补历史。
- [ ] 对明确时间段执行重新匹配，确认预览数量正确、作业最终离开 `running` 状态且人工备注不被清空。
- [ ] 在线索详情中完成“已联系”和“已完成”更新，并确认刷新后状态保留。

### 4. 验证中断与恢复

- [ ] 正常停止并重启 Huginn Leads，确认任务、来源开关和人工状态保留。
- [ ] 主动断开一个 NapCat WebSocket 后恢复，确认产生带起止时间的连接缺口记录。
- [ ] 制造一个可控的处理失败，确认有限重试后进入失败列表，手动重试后重新处理。
- [ ] 停止工作台，使用测试备份执行 `restore.cmd`；确认恢复前数据库被保存为 `before-restore-*`，恢复后记录数量和人工状态一致。

### 5. 连续运行 72 小时

- [ ] 保持两个账号连接，记录每次非计划中断、失败作业、积压峰值和恢复方式。
- [ ] 每 24 小时核对自动备份、数据库完整性、磁盘余量和最近保存时间。
- [ ] 每天抽取启用来源的测试消息，对照“发送数、接收数、保存数、线索数”，登记遗漏和误判原因。
- [ ] 结束时导出脱敏结果，只保留计数、时间和错误码，不复制无关聊天正文。

## 验收标准

- 两个 QQ 的来源、消息、任务、去重和异常记录按 `self_id` 正确隔离。
- 未启用群和未启用联系人正文在业务库及持久日志中的检出数为 0。
- 已启用来源的测试消息无静默丢失；重复事件不产生重复原文或重复线索。
- 匹配、冲突、待核对及多价格结果符合预期，未知信息没有被补成事实。
- 暂停、重启、断线、重跑和人工状态行为符合界面说明。
- 失败作业可见、可重试；重跑最终为 `completed` 或 `failed`，不永久停留在 `running`。
- 备份完整性检查通过，停机恢复成功，且恢复前副本可读。
- 连续 72 小时内无数据损坏、无限重试、持续增长的正常事件诊断或无法解释的积压。

## 停止条件

出现以下任一情况时立即停止真实测试并保留脱敏证据：账号异常或平台限制、Token 泄露、未授权正文被持久保存、数据库完整性失败、恢复失败或磁盘余量不足。
